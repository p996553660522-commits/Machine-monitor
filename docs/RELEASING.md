# Выпуск новой версии

## Постоянные правила

Релизы описаны в `releases.json`; GitHub Actions `.github/workflows/releases.yml` запускает проверки на push в main и PR. Публикация разрешена только main после успешной проверки. `GITHUB_TOKEN` используется кратковременно с contents:write; пользовательские токены в коде не нужны.

Каждая версия фиксируется полным SHA. Не перемещать существующие теги, не заменять публичные assets и не исправлять старый номер задним числом. Несовпадение контрольной суммы останавливает процесс. Публикация сначала создаёт draft, загружает проверенные пакеты, затем делает релиз публичным.

## Шаги

1. Измените код, bump `manifest.json` для интеграции или Discovery version для firmware. Обновите CHANGELOG и документацию; при смене истории опишите миграцию и ограничения отката.
2. Запустите Python/frontend/firmware проверки локально и сохраните исправленный исходный снимок отдельным коммитом A. Не включайте в него приватные данные или сборочные файлы.
3. Добавьте запись в `releases.json`: новый уникальный tag (`vX.Y.Z` или `firmware-vX.Y.Z`), version, kind, полный commit SHA A, firmware строку, history_schema, latest/prerelease и путь notes. Для новой стабильной интеграции latest=true, у прежней latest=false. Для firmware latest=false.
4. Добавьте `release_notes/<tag>.md`, обновите `docs/VERSIONS_RU.md` и CHANGELOG. Сохраните каталог/документы коммитом B и отправьте main.
5. Actions заново тестирует точные снимки, syntax/JSON и ZIP round-trip, собирает deterministic архивы и публикует теги/Releases с SHA256. Если выпуск прерван, повторный запуск продолжает draft; опубликованные файлы не меняет.
6. Проверьте успешный workflow, скачайте ZIP именно из Release, сравните SHA256 и проверьте его содержимое до установки.
7. Сделайте согласованный HA backup; установите готовые файлы из Release. Разработку/тесты вести локально, не на работающем HA/SMB. Проверьте работу после перезапуска отдельно от stub tests.

Коммит B может кратковременно иметь несогласованный каталог во время подготовки; CI должен завершиться успешно перед установкой. Публикация кодового коммита A без записи новой версии намеренно не проходит release gate.

## Локальная проверка

Требуются Git, Python 3.14 (CI), Node 22 (CI); Arduino для упаковки исходного sketch не требуется:

```sh
python -B -m unittest discover -s tests -v
python -B scripts/release.py --out dist
```

Скрипт проверяет каждую integration version её собственными тестами, JS syntax, Python AST/JSON, manifest/firmware/schema соответствие, секретные шаблоны и round-trip каждого ZIP. Старые HA stubs не доказывают совместимость со свежим HA; известные ColorSelector проблемы архивных версий явно отмечены в notes. Firmware guards не заменяют компиляцию и электрическую проверку.

ZIP используют постоянные timestamps/order и storage без compression для одинаковых байтов на разных ОС/zlib. `dist/` исключён из Git. Исполняйте `--publish` только в доверенной среде с правом публикации; workflow делает это после проверок. Не печатайте GH_TOKEN и не сохраняйте его в репозитории.

GitHub Releases/Assets сохраняются до удаления владельцем; краткоживущие Actions artifacts не используются как единственный источник установки. Исходные теги и отдельные source ZIP позволяют восстановить выбранную версию.
